# Personal Web App Implementation Instructions

This document is the concrete implementation plan for turning the current
Movie Agent for Letterboxd CLI project into a complete personal-use web app.

Scope: single-user, self-hosted/local-first web application. The app is designed
for the project owner to use with their own Letterboxd account, DashScope/Qwen
API key, and local Letterboxd MCP server.

Non-goals for this version:

- Multi-user public SaaS.
- Letterboxd OAuth or shared account management.
- Payment, invite, admin, or team features.
- Native iOS/Android app.

## 1. Target Product

Build a web interface that lets the owner:

1. Check Letterboxd account connection status.
2. Enter a current movie mood in natural language.
3. Receive personalized recommendations generated by the existing crewAI
   pipeline.
4. View recommendations as readable movie cards.
5. Add selected films to Letterboxd watchlist.
6. Mark selected films as watched.
7. Rate or like films.
8. Write a review after explicit confirmation.
9. Keep local recommendation history for later review.

The first screen should be the actual working app, not a marketing landing page.

## 2. Recommended Stack

Use the existing project as the root repository.

Backend:

- FastAPI
- Uvicorn
- Existing `src/movie_rec` package
- Existing Letterboxd MCP Node server
- SQLite for local history

Frontend:

- Vue 3
- Vite
- TypeScript
- Pinia
- Vant UI for mobile-friendly controls

Runtime:

- Backend: `http://127.0.0.1:8000`
- Frontend dev server: `http://127.0.0.1:5173`
- MCP server: keep current behavior, usually `http://127.0.0.1:3000/sse`

## 4. Backend Instructions

### 4.1 Add Backend Dependencies

Create `web/backend/requirements.txt`:

```text
fastapi
uvicorn[standard]
pydantic
python-dotenv
aiosqlite
```

The root `requirements.txt` already contains the AI and MCP dependencies. In
development, install both:

```bash
pip install -r requirements.txt
pip install -r web/backend/requirements.txt
```

### 4.2 Create FastAPI App

Create `web/backend/app/main.py`.

Responsibilities:

- Initialize FastAPI.
- Enable CORS for `http://127.0.0.1:5173` and `http://localhost:5173`.
- Include routers for auth, recommendations, Letterboxd actions, and history.
- Expose `GET /api/health`.

Required routes:

```text
GET  /api/health
GET  /api/auth/check
POST /api/recommendations
GET  /api/recommendations/{job_id}
POST /api/letterboxd/watchlist
POST /api/letterboxd/watched
POST /api/letterboxd/rate
POST /api/letterboxd/like
POST /api/letterboxd/review
GET  /api/history
GET  /api/history/{id}
DELETE /api/history/{id}
```

### 4.3 Runtime Management

Create `web/backend/app/core/runtime.py`.

Implement a single-user runtime manager that owns:

- One active MCP session per request, or one shared session guarded by a lock.
- A recommendation job registry.
- Background task status.

For the first version, prefer one MCP session per recommendation request because
it matches the existing CLI lifecycle and reduces state leakage.

Pseudo-flow:

```python
async def run_recommendation(mood: str, watchlist_only: bool = False) -> str:
    external_url = os.getenv("LETTERBOXD_MCP_URL", "") or None
    async with mcp_session(external_url) as session:
        ok, user_or_error = await preflight_check(session)
        # Continue with warning if reads fail, same as CLI.
        crew = MovieCrew(session=session, mood=mood)
        return crew.run()
```

Important: `MovieCrew.run()` is synchronous and may block. In FastAPI, execute it
in a worker thread:

```python
result = await asyncio.to_thread(crew.run)
```

### 4.4 Recommendation API

Create `web/backend/app/services/recommendation_service.py`.

Implement:

- `create_recommendation_job(mood: str) -> RecommendationJob`
- `get_recommendation_job(job_id: str) -> RecommendationJob`

The first version may be polling-based:

1. `POST /api/recommendations` creates a job and starts a background task.
2. Frontend polls `GET /api/recommendations/{job_id}` every 1-2 seconds.
3. Job status is one of `queued`, `running`, `succeeded`, `failed`.

Response shape:

```json
{
  "job_id": "uuid",
  "status": "succeeded",
  "mood": "想看王家卫那种但轻一点",
  "result_text": "...",
  "movies": [],
  "error": null,
  "created_at": "2026-05-21T20:00:00+08:00",
  "finished_at": "2026-05-21T20:01:20+08:00"
}
```

Keep `result_text` as the source of truth for v1. Extracting structured movie
cards from agent output can be added after the basic flow works.

### 4.5 Structured Movie Cards

For v1.5, update task prompts so the final answer includes a JSON block:

```json
{
  "recommendations": [
    {
      "title": "Her",
      "year": 2013,
      "slug": "her-2013",
      "director": "Spike Jonze",
      "reason": "Why this matches the mood.",
      "letterboxd_url": "https://letterboxd.com/film/her-2013/"
    }
  ]
}
```

Backend should parse this into `movies`. If parsing fails, keep displaying
`result_text`.

Do not rely on fragile title-only matching for write actions. Write actions must
use verified Letterboxd slugs.

### 4.6 Letterboxd Action API

Create `web/backend/app/services/letterboxd_service.py`.

Each write API must:

1. Require `confirmed: true` in request body.
2. Require a film `slug`.
3. Open or reuse an MCP session.
4. Call the corresponding existing MCP-backed tool.
5. Return success or error.

Request examples:

```json
{
  "slug": "her-2013",
  "confirmed": true
}
```

```json
{
  "slug": "her-2013",
  "rating": 4.5,
  "confirmed": true
}
```

```json
{
  "slug": "her-2013",
  "review": "Tender, lonely, and strangely comforting.",
  "confirmed": true
}
```

The frontend must show a confirmation dialog before sending `confirmed: true`.

### 4.7 Local History

Use SQLite at:

```text
web/backend/data/movie_rec.sqlite3
```

Create table:

```sql
CREATE TABLE IF NOT EXISTS recommendation_history (
  id TEXT PRIMARY KEY,
  mood TEXT NOT NULL,
  result_text TEXT NOT NULL,
  movies_json TEXT NOT NULL DEFAULT '[]',
  status TEXT NOT NULL,
  error TEXT,
  created_at TEXT NOT NULL,
  finished_at TEXT
);
```

Save every successful recommendation. Optionally save failed jobs for debugging.

### 5.2 App Layout

Use a mobile-first app shell with a compact desktop layout.

Primary navigation:

- Home
- History
- Settings

The Home page is the main app:

- Account status strip.
- Mood input.
- Quick mood chips.
- Submit button.
- Loading timeline.
- Latest recommendation result.

Do not build a landing page.

### 5.3 Core Pages

`HomePage.vue`:

- Shows `AccountStatus`.
- Lets the user type mood text.
- Sends `POST /api/recommendations`.
- Polls job status.
- Navigates or scrolls to results when complete.

`RecommendationPage.vue`:

- Shows result text.
- Shows movie cards when structured data exists.
- Each card has action buttons:
  - Add to watchlist.
  - Mark watched.
  - Rate.
  - Like.
  - Review.

`HistoryPage.vue`:

- Lists local recommendation history.
- Allows opening a past result.
- Allows deleting a history item.

`SettingsPage.vue`:

- Shows environment-derived configuration status only.
- Do not expose raw secrets in the browser.
- Show whether required variables appear configured:
  - `DASHSCOPE_API_KEY`
  - `LETTERBOXD_USERNAME`
  - `LETTERBOXD_PASSWORD` or `LETTERBOXD_CREDENTIALS` or `LETTERBOXD_COOKIE`
  - `TMDB_API_KEY`

### 5.4 Frontend API Client

Create `src/api/client.ts`:

```ts
export const API_BASE =
  import.meta.env.VITE_API_BASE ?? "http://127.0.0.1:8000";

export async function apiJson<T>(
  path: string,
  options: RequestInit = {}
): Promise<T> {
  const res = await fetch(`${API_BASE}${path}`, {
    headers: {
      "Content-Type": "application/json",
      ...(options.headers ?? {}),
    },
    ...options,
  });

  if (!res.ok) {
    const text = await res.text();
    throw new Error(text || `Request failed: ${res.status}`);
  }

  return res.json() as Promise<T>;
}
```

### 5.5 UI Requirements

Use an app-like interface:

- No marketing hero page.
- No decorative card-heavy landing layout.
- Use real controls for real actions.
- Use confirmation dialogs for account mutation.
- Keep mobile width polished.
- Keep desktop readable with a max content width around `960px`.

Important states:

- Backend offline.
- Letterboxd not authenticated.
- Recommendation running.
- Recommendation failed.
- Empty history.
- Action succeeded.
- Action failed.

## 6. Security Rules

This is a personal-use app, but still follow these rules:

1. Never send raw API keys or Letterboxd password to the frontend.
2. Keep secrets in `.env`.
3. Do not log passwords, cookies, or API keys.
4. Require explicit frontend confirmation for all Letterboxd writes.
5. Bind local development servers to `127.0.0.1` unless intentionally exposing.
6. If deploying publicly, add authentication before deployment.

For personal remote access, prefer a private VPN, Tailscale, or a password
protected reverse proxy.

## 7. Development Order

Follow this order exactly.

### Milestone 1: Backend Skeleton

Deliverables:

- `GET /api/health` returns `{ "ok": true }`.
- FastAPI starts with Uvicorn.
- CORS works from Vite.

Verification:

```bash
uvicorn web.backend.app.main:app --reload --host 127.0.0.1 --port 8000 --loop asyncio
curl http://127.0.0.1:8000/api/health
```

### Milestone 2: Auth Check

Deliverables:

- `GET /api/auth/check` calls existing `preflight_check`.
- Response includes `ok`, `username`, and `error`.

Verification:

```bash
curl http://127.0.0.1:8000/api/auth/check
```

### Milestone 3: Recommendation Job

Deliverables:

- `POST /api/recommendations` accepts `{ "mood": "..." }`.
- Backend starts a job.
- `GET /api/recommendations/{job_id}` returns status.
- Successful job returns `result_text`.

Verification:

```bash
curl -X POST http://127.0.0.1:8000/api/recommendations \
  -H "Content-Type: application/json" \
  -d '{"mood":"想看轻松但有余味的电影"}'
```

### Milestone 4: Basic Frontend

Deliverables:

- Vue app starts.
- Home page can submit mood.
- Loading state is visible.
- Final result text is displayed.

Verification:

```bash
cd web/frontend
npm run dev
```

Open `http://127.0.0.1:5173`.

### Milestone 5: Letterboxd Write Actions

Deliverables:

- Watchlist action works.
- Watched action works.
- Rating action works.
- Review action works.
- Every action uses confirmation dialog.

Verification:

- Test with one known film slug.
- Confirm account changes on Letterboxd.

### Milestone 6: History

Deliverables:

- Successful recommendations are saved to SQLite.
- History page lists previous recommendations.
- User can open and delete history entries.

### Milestone 7: Polish

Deliverables:

- Mobile layout is clean.
- Desktop layout is clean.
- Error messages are understandable.
- README includes web startup commands.


## 10. Acceptance Criteria

The implementation is complete when:

1. The user can open the web app locally.
2. The app shows whether Letterboxd auth works.
3. The user can enter a mood and receive a recommendation.
4. The page remains responsive while the recommendation runs.
5. Recommendation results are saved locally.
6. The user can perform Letterboxd write actions only after confirmation.
7. Secrets never appear in frontend responses or browser logs.
8. The README documents how to start backend and frontend.
